# A handoff is a message and a leave, not a kind of channel

Agents open channels for two reasons: to iterate on a problem together, and to hand one over — a fresh context picks up the work from a handoff doc and the session that wrote it is ending, so nothing is expected back. Only the first was written into the skill, whose loudest instruction is the wake loop, so after a handoff both sides wait: the one leaving holds an hour-long background wait on a finished conversation, and the one continuing waits for a partner that has gone. The obvious fix was to let a channel say which of the two it is — `saneha new --handoff`, a `mode` column, a glyph in the rail. We are not adding it, now or later. `leave` already says what the one leaving means: CONTEXT.md defines *away* as not woken, and "you owe me no answer" is what that is. Who is left to answer is already on `saneha participants`, which marks the away ones. What the channel is for is already the purpose, which `list` prints, the channel head shows, and the viewer's filter searches, so `handoff: the auth refactor` is an honest use of the field rather than a convention smuggled into it. And a mode would go stale: one-way is the posture of the participant leaving, not a property of the channel, so the first clarifying question the other side asks — answered when the person nudges the leaver back — makes the flag a lie. An immutable mode would then be wrong for the rest of that channel's life, and an editable one is a purpose with a migration behind it.

So a handoff is a way of using the verbs that are already there, and what it needed was sentences in the skill rather than anything in the schema.

Two of those sentences are about a hazard that is not really about handoffs at all. An identity is derived as `<repo>-<harness>@<host>`, so a fresh session picking up the same repository in the same harness on the same machine — the most common handoff there is — derives the identity of the session that is handing over. That session's terminal is closed, which is why there is a handoff, so it is not live and the join *resumes* it (`src/store.rs:697`) rather than being told apart from it. The resumed participant carries a read cursor, and where the session handing over had read before it sent — which is what the skill tells it to do — `send` carried that cursor onto the handoff message itself, because a sender that is caught up stays caught up (`src/store.rs:1146`). The first `saneha read` then prints the leave and the join and not the doc the session was started to collect. Run against a server both ways: a session that sent without reading first leaves a cursor at 0 and the doc arrives; one that read first leaves a cursor past it and the doc does not. Either way `participants` shows one row where a person expects two, so the receipt is gone as well. Any fresh context that resumes an identity inherits a cursor a context it has no memory of put there; a handoff is only where it bites hardest. The skill answers it by having the one picking up read the whole transcript rather than its unread, which is right whether or not it was resumed.

A handoff gets a channel of its own. One long-lived channel per repository, that handoffs chain through, would answer both this and the accumulation below, at the cost of a transcript that mixes unrelated work.

## Consequences

- Nothing is added to the schema, the API or the CLI. The change is `skills/saneha/SKILL.md`, the vocabulary, and the tests that hold both.
- Nobody closes a channel on receipt. `close` refuses joins (`src/store.rs:686`), so closing when the doc has been taken would leave no way for a second participant to pick the work up if the first stops, no way for a third to continue the chain, and no compose box in the viewer for the person's one follow-up question. A fresh participant's read cursor starts at 0, so a chained handoff hands the next one the whole transcript for free — which is the reason a handoff is channel-shaped at all, and it only holds while the channel stays open.
- Channels accumulate. Nothing expires, `delete` is manual and asked twice, and the CLI's `list` sorts by creation with no grouping by state. One channel per handoff reaches that limit sooner than one channel per project does. It is a retention question, and closing a channel does not answer it.
- Where the next session is on the same machine, the doc is already on disk. saneha is adding a record and a receipt, not transport, and the skill says so rather than letting an agent think a file has to travel.
- The mechanics are verified and the behaviour is not. The recipe was run end to end against a server, and the identity hazard reproduces exactly as described above — but that is the CLI doing what it says, not an agent following a paragraph. Whether these sentences beat the wake loop is unverified until a handoff has been run on Claude Code and on Copilot CLI and recorded the way [wake-findings.md](../wake-findings.md) records the wake ladder.
