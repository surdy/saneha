# The binary resolves the server, not the shell

`SANEHA_URL` was the only way to say where the server is for the whole of v1, and the documented way to make it stick was [an export in a shell profile](../deploy.md). That works for a person and is unreliable for an agent. A harness runs each command in a fresh non-interactive shell, and whether such a shell reads a profile depends on the harness and on the shell — so the address is there when the person tries it by hand and missing when the agent tries the same thing a second later, with nothing on either side saying why. What an agent does then is ask, which costs a round trip and only works if somebody is there.

So the binary resolves the address rather than the shell. `saneha init --url <URL>` writes it to `$XDG_CONFIG_HOME/saneha/config.json`, falling back to `~/.config`, in the same shape [`server::default_database_path`](../../src/server.rs) already uses for the database. `init` is where it goes because `init` is already the step taken once per machine, so this is not a new thing to remember; and it is the same reasoning as [ADR-0006](0006-the-installed-skill-is-a-pointer.md), one hop further out. The instructions moved into the binary so a harness's loader could not hand an agent a stale copy. The address moves into the binary so a harness's shell cannot fail to hand it over at all.

**The environment still wins.** The order is `SANEHA_URL`, then the file, then an error naming both fixes. This is not a courtesy to existing scripts: `tests/support` points every child at a server on a port the OS picked, the deploy scripts name the server they mean, and a one-off against a local `saneha serve` is a prefix on one command. All three have to go on beating whatever this machine was configured with, and the last of them is also the answer to wanting a second server at all.

JSON rather than TOML because `serde_json` is already a dependency and a configuration format is not worth another one. Keys this binary does not know are read and written back untouched, so a file written by a newer saneha survives an older one rewriting it.

## Consequences

- **An unset `SANEHA_URL` used to be a safety catch, and this removes it.** It is why a stray agent could not blunder into production: with no address, nothing happened. Now every agent on a configured machine reaches the configured server by default, which is the entire point of the change and also its whole risk. The mitigation is that the second server stays a prefix — the thing you are most likely to want to protect is reached deliberately, not by default — but a machine configured to point at production is a machine where an agent that misreads its instructions is talking to production. That was already true of a shell profile with the export in it, which is what this replaces; it is written down here because it is now the recommended state rather than an accident.
- The skill no longer opens with `SANEHA_URL` as something every verb needs; it describes what an agent will actually meet, which is a verb saying it has no server, on a machine nobody pointed at one. This buys no lines back — the sentence about an `export` not surviving a tool call is still worth its line, and the second-server prefix now needs saying — so the paragraph is the same length and only truer. The error an agent meets names `saneha init --url` rather than only telling it to ask the person; an agent on an unconfigured machine still has to ask, and still can.
- `saneha init` now has two jobs, and a run without `--url` must leave the address alone rather than clear it — otherwise the run that brings the pointers up to date would silently unconfigure the machine. There is a test for exactly that.
- **An address saved wrong is durable**, where a typo in `SANEHA_URL` is gone with the shell. So `--url` parses what it is given and requires a host before writing, which is stricter than any verb is about the environment. `Remote::at` strips a trailing slash before it looks for a scheme, so a lone `http://` reaches it as `http:` and comes back as `http://http:` — which parses, names a host, and is nothing anybody meant. The check is made against what was typed for that reason.
- Nothing is offered for naming several servers, and a channel name stays a whole address. That is what makes a handoff work: the skill says to print the channel name for the person to pass on, `/c/<channel>` is a link you can send to a phone, and a fresh session is started with nothing but a name. Named servers would mean a name no longer says where, and every handoff would have to carry two things instead of one — paid on every handoff, to buy what a one-command prefix already gives.
